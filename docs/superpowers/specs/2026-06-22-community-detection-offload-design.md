# Вынос community-detection из Neo4j — дизайн

**Дата:** 2026-06-22
**Статус:** дизайн (на ревью)
**Трек:** Tier 1 / следствие контеншн Neo4j

## Проблема

Ребилд графа сообществ (`CommunityBuildWorkflow` → `detect_communities_activity` → `src/graph/communities.py`) гоняет GDS Leiden **внутри JVM-heap Neo4j**. С ростом графа `__Entity__` он падает с `OutOfMemoryError: Java heap space` даже при heap 32G. Подтверждённые драйверы (код + фактическая ошибка + размерно-зависимый onset):

- GDS-проекция копирует **весь** граф `__Entity__` в JVM-heap, двунаправленно (`undirectedRelationshipTypes: ['*']` → каждое ребро дважды), **без оценки памяти и без кэпа** (`communities.py`, `_project_cypher`).
- `gds.leiden.stream` идёт с `includeIntermediateCommunities: true` → в heap держится весь дендрограмм (сообщество на каждом уровне, на каждую ноду) — самый тяжёлый одиночный вклад.
- При падении чистка проекции — **best-effort**, а `FAST_RETRY` повторяет 3×, каждый раз заново строя проекцию и умножая удар по ресурсам.

Ключевое: любой подход, который держит **весь граф в памяти за один проход**, лишь отодвигает стену по мере роста графа. Фикс обязан **увести память из Neo4j** и сделать её независимо масштабируемой.

## Решение (зафиксировано на brainstorming)

- **Вынести кластеризацию из JVM Neo4j** в существующий Temporal-воркер `kb-graph-build`, на **`leidenalg` поверх `python-igraph`** (нативный иерархический Leiden, семантика совместима с `gds.leiden`: вес рёбер, resolution=gamma, уровни).
- **Глобальная иерархия — жёсткое требование** (GraphRAG: drill-down по уровням + глобальные summary) → сохраняется: leidenalg даёт многоуровневую иерархию.
- **Opt-in, измеренный swap** (политика проекта: бенчмарк до внедрения; никогда не слепая замена). Бэкенд выбирается флагом конфига; дефолт остаётся `gds`, пока не пройдёт **строгий бенчмарк паритета**, затем флип на `leidenalg`.
- Вне scope (на будущее): инкрементальное поддержание иерархии; партиционирование/распределённая кластеризация (потолок RAM на воркер далёкий и изолированный — возвращаемся, только когда упрёмся в один воркер).

## Архитектура

Меняется **только шаг вычисления**. Output-контракт (ноды `:Community`, membership, уровни иерархии) и весь downstream (суммаризация сообществ, vector-индекс отчётов) — **без изменений**: новый бэкенд отдаёт строки в том же виде, что и старый `gds.leiden.stream`, поэтому существующая материализация переиспользуется дословно.

```
detect_communities / detect_hierarchy (communities.py)
  └─ backend = settings.<...>.community_backend   # "gds" | "leidenalg"
       ├─ "gds"       → существующая GDS-проекция + gds.leiden.stream   (без изменений)
       └─ "leidenalg" → 1. стрим рёбер из Neo4j (батчами)
                        2. построить igraph, иерархический leidenalg   (в RAM воркера)
                        3. отдать строки {name, communityId, intermediateCommunityIds}
  └─ общая материализация / запись назад  (без изменений)
```

### Компоненты (каждый тестируется независимо)

1. **Edge-extractor** — стримит `(s.name, t.name, weight)` по `(:__Entity__)-[r]->(:__Entity__)` батчами (keyset-пагинация по element id или `apoc.periodic.iterate`), чтобы чтение не материализовало один гигантский результат. Возвращает итерируемые рёбра + множество нод. **GDS-проекция не строится.** Вход: graph store. Выход: рёбра/ноды. Зависит от: драйвер Neo4j.

2. **Clusterer (`leidenalg` + `python-igraph`)** — строит взвешенный неориентированный igraph и гоняет иерархический Leiden. Resolution = `community_leiden_gamma`, фиксированный seed (паритет с текущим `randomSeed: 19`), многоуровневая агрегация для эквивалента `intermediateCommunityIds`. CPU-bound → выполняется в `asyncio.to_thread` под heartbeat-таймером. Вход: рёбра/ноды + параметры. Выход: на ноду (communityId, ids уровней). Зависит от: leidenalg, igraph. Чистая функция от входов (тестируется оффлайн).

   **Ключевой риск реализации (проверить рано в плане):** GDS `includeIntermediateCommunities` отдаёт внутренние уровни агрегации Leiden напрямую; `leidenalg` через `find_partition` даёт плоский разбор, поэтому многоуровневую иерархию надо реконструировать через цикл агрегации оптимайзера (`Optimiser.optimise_partition` по агрегированным графам) или повторные resolution. Это место наиболее вероятного расхождения с иерархией GDS — паритет проверяется бенчмарком до флипа дефолта.

3. **Output-adapter** — маппит выход clusterer'а в существующий вид строк (`name`, `communityId`, `intermediateCommunityIds`), который потребляет текущая материализация. Изолирует swap бэкенда от записи.

4. **Backend-selector** — переключатель конфига `community_backend` в `detect_communities` / `detect_hierarchy`; оба пути возвращают идентичные типы.

### Упрочнение оркестрации (заодно чинит сброс таски)

- Задать явный `heartbeat_timeout` на `detect_communities_activity` и слать heartbeat в процессе кластеризации (теперь она in-process, так что реальный hang детектится, а не ждёт `start_to_close`).
- **Не ретраить вслепую** ресурсные ошибки (сейчас `FAST_RETRY` × 3 умножает удар). Считать OOM/ресурсные ошибки non-retryable (или одна попытка); ретраи — только для транзиентных/транспортных.
- Память теперь в процессе воркера (сайзится независимо через пул/контейнер `kb-graph-build`); heap Neo4j больше не потолок, и OOM кластеризации больше не дестабилизирует БД, обслуживающую живой поиск.

## Бенчмарк и eval (строгий паритет — гейт для флипа дефолта)

Расширить `tests/eval/`:

- На репрезентативном подграфе `__Entity__` прогнать **оба** бэкенда и сравнить: **модулярность**, **число сообществ**, **распределение размеров**, **время**, **пиковую память** (RSS воркера для leidenalg; heap Neo4j для GDS).
- **Критерий флипа дефолта → `leidenalg`:** сопоставимое качество (модулярность в пределах согласованного допуска; число/размеры сообществ не патологически иные) И существенно меньшая память Neo4j.
- Пока бенчмарк не пройден — **дефолт `community_backend = "gds"`**.

## Конфиг / зависимости

- Новые зависимости: `python-igraph`, `leidenalg`.
- Новый конфиг: `community_backend: Literal["gds","leidenalg"] = "gds"` (env-overridable). Переиспользовать существующие `community_leiden_gamma`, seed, `community_max_levels`, `community_min_size`.
- GDS-плагин **остаётся** (его используют другие analysis-инструменты — PageRank и т.п.); просто `gds.leiden` для детекции сообществ уходит с дефолтного пути после флипа.
- `requirements.txt` перегенерировать.

## Обработка ошибок

- Сбои edge-extraction (транспорт Neo4j) → retryable (транзиентные).
- Сбои clusterer'а (ресурсные/value) → non-retryable; логировать с размером графа, чтобы потолок масштаба был виден.
- Swap бэкенда обратим в любой момент через флаг конфига (тот же output-контракт).

## Тестирование

- Unit: clusterer — чистая функция от (рёбра, параметры) → детерминированные тесты с фиксированным seed на малых графах (санити модулярности, структура уровней, учёт весов).
- Unit: форма output-adapter'а совпадает с контрактом входа материализации.
- Интеграция (gated на Neo4j): edge-extractor корректно стримит; end-to-end `detect_communities` с `community_backend=leidenalg` пишет ту же структуру `:Community`, что и GDS-путь, на малом графе.
- Eval/бенчмарк: сравнение строгого паритета выше.

## Вне scope (заметки на будущее)

- **Инкрементальная иерархия** — дёшево приписывать новые сущности к существующим сообществам; редкая/локальная перекластеризация; убирает частоту полного пересчёта.
- **Партиционирование / распределённость** — когда RAM одного воркера превышена: divide-and-conquer (иерархии по регионам + глобальный верх) или распределённый движок.
