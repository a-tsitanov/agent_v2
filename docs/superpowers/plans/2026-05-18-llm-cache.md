# LLM response cache — survive activity retries without paying LLM twice

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** When a Temporal activity that has already paid for N LLM calls fails on call N+1 and Temporal retries the activity from scratch, **call results from the previous attempt are served from cache** instead of re-hitting the model.  Covers all LLM call paths (extract_kg, merge_kg summary, ER judge, translator) with zero changes to project code.

**Architecture:**  LiteLLM proxy has built-in caching with Redis backend.  We're already routing every LLM call through LiteLLM (`http://localhost:4000`), so flipping its `cache_params` to point at a Redis container gives us project-wide caching by `(model, prompt, params)` hash.  Activity code, prompts and Temporal retry policy stay untouched — cache lookup happens transparently at the proxy boundary.

**Tech Stack:** LiteLLM proxy (existing), Redis 7 (new docker service), `OpenAILike` client (no change), Temporal worker (no change).

**Spec context:** Workflow durability story in `docs/superpowers/specs/2026-05-15-ingest-temporal-workflow-design.md` §7.  Retry policy in `src/workflow/document_ingest.py` (forever-retry + per-activity `schedule_to_close`).  LiteLLM config: `docker/litellm_config.yaml`.

**Session protocol:** Pause after each labelled **Stage** for sync.

**Why this and not the alternatives:**

| Option | Effort | Cross-workflow benefit | Code touched |
|---|---|---|---|
| **LiteLLM cache (this plan)** | 1 commit | yes (proxy-side) | config only |
| Heartbeat-resume in `extract_kg` | days | no (per workflow run) | activity refactor |
| In-project KV cache | days | partial (MinIO blob) | new module + tests |
| Per-doc Postgres cache | days | yes | schema + new module |

LiteLLM cache wins on every axis for the retry-savings use case. The
remaining options are valid for *forward-progress* mid-activity
(resuming a doc's extraction from chunk 50/100 mid-attempt), but
Temporal retries the whole activity anyway — the proxy-side cache
makes the retry near-instant for the chunks already done.

### Task 2: Turn caching on in `docker/litellm_config.yaml`

**Files:**
- Modify: `docker/litellm_config.yaml`.

- [ ] **Step 1: Add `litellm_settings.cache`**

Append to the file (after `model_list`):

```yaml
litellm_settings:
  # Cache key includes (model, messages, temperature, max_tokens, ...)
  # so identical retries hit; different model / temperature / prompt
  # naturally miss.  TTL bounds staleness — operator can tune.
  cache: true
  cache_params:
    type: redis
    host: redis            # docker-compose service name
    port: 6379
    ttl: 86400             # 24h
    # Optional namespace so multiple kb-llamaindex environments
    # sharing a Redis don't clobber each other.
    namespace: "kb-llamaindex"
```

LiteLLM keys the cache on (model, messages, temperature, max_tokens, …).  If we send a different temperature or include a unique timestamp/UUID in the prompt, every retry misses.  Audit current call sites.

**Files:**
- Modify: `src/retrieval/llm.py` — pin `temperature=0.0` and pass a stable seed where the provider supports it.
- Test: extend an existing unit test to assert the kwargs.

- [ ] **Step 1: Audit non-determinism in prompts**

```bash
grep -rn "datetime\.now\|time\.time\|uuid\.\|prompt.*format" \
    src/graph/lightrag_prompts.py src/retrieval/ \
    src/graph/merge.py src/graph/entity_resolution.py \
```

Anything that injects a per-call timestamp or fresh UUID into the

- [ ] **Step 2: Pin temperature + seed in `build_llm()`**

In `src/retrieval/llm.py`:

```python
return OpenAILike(
    model=cfg.llm_model,
    api_base=cfg.base_url,
    api_key=cfg.api_key.get_secret_value(),
    timeout=cfg.timeout_s,
    max_retries=cfg.max_retries,
    is_chat_model=True,
    is_function_calling_model=function_calling,
    temperature=0.0,
    # OpenAI-compatible providers accept this; LiteLLM passes it
    # through.  Ollama ignores; vLLM honours.  Same seed → same
    # output for the same model + prompt + temperature.
    additional_kwargs={"seed": 0},

```

```python
    llm = build_llm()

    # Some LlamaIndex versions stash `additional_kwargs`; others
```

### Task 5: Cache namespacing per prompt-template version

Problem: when we edit a prompt template (e.g. add a sentence to the
LightRAG extractor prompt), every cached response becomes stale —
but LiteLLM still serves them since the message bodies are
identical from the proxy's view.

Solution: prefix every system prompt with a deterministic version
sentinel: `[v=2026-05-18-r3]` injected at template-load time.  When
we ship a prompt change, bump the sentinel; cache naturally misses.

## Gotchas to watch for

1. **Tool calling responses are cached too.** When an LLM returns a
   tool-call JSON, the tool name + arguments must be deterministic
   for the cache key to be stable.  If our agent prompts inject
   timestamps into the user message ("сегодня 2026-05-18, ответь…"),
   cache misses every day.  Audit `react_agent.py` and friends — for
   the search side the cache may yield less benefit anyway.
2. **Embeddings**: LiteLLM cache covers `/v1/embeddings` too with
   the same `cache: true` flag.  Bonus win — re-embedding the same
   chunks during ER on retry becomes free.
3. **`seed` field**: Ollama ignores it, vLLM honours.  Without
   honouring, temperature=0 alone often suffices for determinism in
   modern models.  Don't depend on seed; treat it as belt-and-braces.
4. **Cache size**: 24h TTL on 8k-token responses × thousands of
   unique chunks → low GB.  Trivial.  `maxmemory-policy allkeys-lru`
   in Redis ensures graceful eviction if it ever pressures memory.
5. **Concurrent cache stampede**: 10 parallel summary calls all
   firing the same prompt simultaneously may all miss before any
   warms the cache.  Acceptable cost on first attempt; retry is
   still fast.  If a problem, LiteLLM has request coalescing in
   newer versions — check upgrade notes before relying on it.
6. **Sensitive prompts**: cached responses live in Redis as
   plaintext.  Project doc content + LLM responses are sensitive in
   most deployments.  In production, run Redis on the same network
   namespace as LiteLLM (already the case in docker-compose), or
   use `requirepass`.
