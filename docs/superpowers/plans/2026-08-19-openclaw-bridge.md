# Мост к openclaw: план

Дата: 2026-08-19. Третий кусок телеграм-бота; первый закрыт, второй (задачи) пропущен сознательно.

## Зачем

`/ask` всегда зовёт один `kb_search`. Агент openclaw выбирает из 25 инструментов и комбинирует
несколько. Проверено 2026-08-19 на живом ходе: вопрос «сколько сущностей в графе» — агент сам
позвал `kb-tools.graph_stats` и `kb-search.kb_analyze`, 0 сбоев, 59 секунд. Бот так не умеет и
не будет уметь без переписывания в агента.

## Снятая схема протокола

Проверено на живом шлюзе `2026.7.1`, протокол версии 4.

Транспорт — WebSocket на `:18789`, любой путь (`/`, `/ws`, `/gateway` — всё принимается).

**1. Сервер сразу шлёт вызов:**

```json
{"type":"event","event":"connect.challenge","payload":{"nonce":"…","ts":1787135022358}}
```

**2. Клиент отвечает:**

```json
{"type":"req","id":"<uuid>","method":"connect","params":{
  "minProtocol":4,"maxProtocol":4,
  "client":{"id":"cli","version":"0.1.0","platform":"linux","mode":"cli"},
  "role":"operator","scopes":["operator.read","operator.write"],
  "auth":{"token":"<OPENCLAW_GATEWAY_TOKEN>"}}}
```

`client.id` — только `cli` или `vscode`, иначе отказ. `client.mode` — только `cli`.
`platform` и `mode` обязательны. Всё это выяснено по сообщениям валидации самого шлюза.

**3. Ответ `hello-ok`:**

```json
{"type":"res","id":"…","ok":true,"payload":{"type":"hello-ok","protocol":4,
  "server":{"version":"2026.7.1","connId":"…"},
  "auth":{"role":"operator","scopes":[]},
  "policy":{"maxPayload":26214400,"maxBufferedBytes":52428800,"tickIntervalMs":30000},
  "features":{"methods":[…]}}}
```

**Формы кадров:** запрос `{type:"req",id,method,params}`, ответ `{type:"res",id,ok,payload|error}`,
событие `{type:"event",event,payload,seq?}`. Ошибка — `{code,message,details?,retryable?}`.

**Методы чата** (из `features.methods`): `chat.send`, `chat.abort`, `chat.history`,
`chat.startup`, `chat.metadata`, `chat.message.get`.

`sessionKey` на проводе имеет вид `agent:<agentId>:<ключ>` — CLI превращает `--session-key foo`
в `agent:main:foo`.

Финальный текст ответа лежит в `result.payloads[0].text` (подтверждено на выводе CLI `--json`).

## Нерешённое, и это риск номер один

Handshake проходит (`ok:true`, роль `operator`), но **`scopes` приходят пустыми**, и `chat.send`
отвечает `missing scope: operator.write`. Токен при этом верный — сверен с окружением контейнера.

Документация говорит: «для token/password авторизации выдаётся полный набор operator-scopes».
Значит наш ответ не распознан как shared-secret bearer. Рабочая гипотеза: сервер прислал `nonce`,
а мы его проигнорировали — вероятно, требуется подпись nonce, а не голый токен.

**Пока это не решено, моста нет.** Всё остальное в плане зависит от шага 1.

## Шаги

### Шаг 1. Получить scopes (блокирующий)

Разобраться, как выдаётся `operator.write`. Порядок проверки, от дешёвого к дорогому:

1. Подписать `nonce` токеном (HMAC-SHA256) и передать в `auth` — самая вероятная форма.
2. Посмотреть, что шлёт сам CLI: поднять шлюз с `--ws-log compact` в **отдельном** контейнере на
   другом порту, чтобы не трогать рабочий, и выполнить против него один `openclaw agent`.
3. `gateway.auth.identityScopes` в конфиге — но он для trusted-proxy/Tailscale, нам не подходит.

Критерий готовности: `chat.send` с пустыми params отвечает ошибкой **валидации схемы**, а не
отказом по scope. Тогда же из этой ошибки снимем точные параметры `chat.send`.

### Шаг 2. Клиент шлюза

`src/bot/openclaw_client.py`, около сотни строк:

- `ask(question, session_key, timeout) -> {"text": str, "run_id": str}`
- handshake, `chat.send`, чтение событий до финального `res`, разбор текста
- `abort(run_id)` через `chat.abort`
- при подключении сверять `payload.protocol == 4` и падать явно при расхождении — протокол не
  публичный контракт, обновление openclaw не должно ломать нас молча

Зависимость одна: `websockets` (уже стоит в окружении, в образ бота добавить).

Тесты: фейковый WebSocket-сервер на тех кадрах, что сняты выше. Handshake, успешный ход,
отказ по scope, таймаут, разрыв соединения.

### Шаг 3. Команда `/agent`

Рядом с `/ask`, не вместо. `session_key` = `tg:<chat_id>` — у агента своя память, наш слой
сессии и переписывания на этом пути не нужен (`chat.history` ведёт её сам).

Тратит квоту и занимает слот наравне с `/ask`: те же ~60 секунд.

Отмена достаётся даром: `chat.abort` уже в протоколе. Команда `/stop` — три строки, если
понадобится.

### Шаг 4. Сравнить и решить

Десяток одинаковых вопросов через `/ask` и `/agent`, сравнить ответы и время. Именно ради этого
`/agent` — отдельная команда: гипотезу «агент лучше» надо проверить, а не объявить.

По результату: агент стабильно лучше — `/ask` переключается на него, прямой поиск остаётся как
`/search`. Не лучше — команда остаётся нишевой, и мы знаем почему.

## Что чинить рядом

**`kb-stats` не подключён к openclaw.** В конфиге только `kb-search` и `kb-tools`. Одна команда
`openclaw mcp add`, но без неё агент статистику не увидит никогда.

**Агент падает через раз.** Первый прогон — 0 сбоев, второй вернул
`Подсистема графа не смогла ответить: Space was not chosen`. Это ошибка сессии Nebula, не агента.
Если воспроизводится — чинить до моста, иначе половина ответов будет мусором.

**Токен шлюза — дефолтный `change-me-strong-key`.** Для внутренней сети терпимо, но бот открыт
внешним клиентам; поменять при выкатке.

## Чего в плане нет

Очереди и фоновых задач — один пользователь, довод прежний.
Замены `/ask` сразу — сначала сравнение.
Своей памяти диалога на пути агента — у него есть своя.
